# TS-080 — Security Event Log Cleared

> Someone wiped the Windows Security log on this machine — usually to cover their
> tracks.

## What it detects

The audit-log-cleared event (Windows Security Event ID `1102`). One occurrence
fires. Windows emits `1102` as the final entry whenever the Security log is
cleared, so the act of erasing the log announces itself. (The companion rule
TS-080-sys catches the System-channel equivalent, Event ID `104`.)

## Why it matters

Clearing event logs is almost never legitimate on a running system — it
destroys the forensic record of what an attacker did. It's a deliberate
anti-forensics step, typically late in an intrusion once the attacker has admin
rights and wants to slow down investigation. A cleared log is both a strong
compromise signal and a sign you may have lost evidence, which is why TinySOCs
ships events off-box continuously.

## What a true positive looks like

A `1102` appearing outside any sanctioned maintenance, often on a server or DC,
sometimes correlated with other high-severity alerts (credential dumping,
service installs) shortly before. The `SubjectUserName` in the event names the
account that did it.

## Common false positives

- **Sanctioned log rotation or compliance tooling** that clears logs by policy.
  Rare on Windows, but if you have it, allowlist the host:
  → allowlist `host: logserver01`.
- **IT troubleshooting** that manually clears a log. Educate against it (it
  destroys evidence); allowlist the host only if genuinely unavoidable.

This rule honours these allowlist scopes (tune without editing the rule):

- `host`
- `host_pattern`

## Tuning knobs

None — single-event trigger. Clearing the Security log should essentially never
be routine; prefer fixing the process over allowlisting.
