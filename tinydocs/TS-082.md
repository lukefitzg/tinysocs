# TS-082 — AMSI Bypass

> A PowerShell script contained code whose only purpose is to blind Windows'
> built-in script scanner (AMSI).

## What it detects

A PowerShell ScriptBlock-logging event (Event ID `4104`) whose script text
contains known AMSI-bypass markers: `AmsiUtils`, `amsiInitFailed`,
`AmsiScanBuffer`, or `SetValue(null`. One occurrence fires. Requires PowerShell
ScriptBlock logging to be enabled (TinySOCs' installer turns it on).

## Why it matters

AMSI (the Antimalware Scan Interface) lets antivirus inspect scripts *after*
they're de-obfuscated, defeating much fileless malware. Attackers neutralise it
with a short snippet that flips an internal flag so AMSI reports "clean" for
everything afterward. There is no legitimate reason for normal scripts to touch
AMSI internals — a match here is a strong indicator of hands-on malicious
PowerShell, the workhorse of fileless attacks.

## What a true positive looks like

A script — often heavily obfuscated, base64-encoded, or downloaded in memory —
patching `AmsiUtils`/`amsiInitFailed` right before running further payload.
Frequently paired with `-EncodedCommand` or download cradles.

## Common false positives

- **Security researchers / red-team tooling** run by your own staff. Allowlist
  the user or host doing sanctioned testing:
  → allowlist `host: redteam-vm` or `user: pentester`.
- **AV/EDR self-tests** that reference AMSI APIs. Rare; allowlist the specific
  host by path/process if confirmed.

This rule honours these allowlist scopes (tune without editing the rule):

- `host`
- `host_pattern`
- `process_path`

## Tuning knobs

None — substring match on known bypass markers. Don't broaden it; allowlist the
sanctioned testing host instead.
