# TS-002 — Brute Force Logon (by source IP)

> One machine is failing to log in over and over — it's spraying guesses across
> accounts from a single source.

## What it detects

Failed-logon events (Windows Security Event ID `4625`) grouped by source IP
address. Fires when one IP accumulates `20` failures within a `5`-minute window.
Where TS-001 counts failures *per account* (catching a focused attack on one
user), TS-002 counts *per source* — catching one attacker trying many accounts,
i.e. password spraying.

## Why it matters

Password spraying deliberately stays under per-account lockout thresholds by
trying a few common passwords against many users. Counting by source IP is the
way to see it: no single account looks attacked, but one IP is clearly working
through your user list. This is a very common entry tactic against exposed
services.

## What a true positive looks like

A single external (or unexpected internal) IP generating failures against a
spread of different usernames, often with `LogonType` 3 (network) or 10 (RDP),
frequently from an unfamiliar geography or hosting provider.

## Common false positives

- **A misconfigured app or appliance** with a stale credential hammering auth
  from one IP. Fix the credential, or allowlist the source:
  → allowlist `source_ip: 10.0.0.42`.
- **A NAT gateway** behind which many legitimate users sit can aggregate benign
  failures. Allowlist the gateway range if it's known:
  → allowlist `source_ip_cidr: 192.168.10.0/24`.

This rule honours these allowlist scopes (tune without editing the rule):

- `source_ip`
- `source_ip_cidr`

## Tuning knobs

`threshold` (default `20`, range `5`–`100`). Behind heavy NAT you may raise it;
on a small flat network you can lower it. Prefer allowlisting a known busy
gateway over globally raising the bar.
