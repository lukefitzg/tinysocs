# TS-020 — Scheduled Task Created

> A new scheduled task was created — a standard way for programs (and attackers)
> to make something run automatically.

## What it detects

A scheduled-task-creation event (Windows Security Event ID `4698`), grouped by
the creating account, firing on first occurrence with a 60-minute cooldown.

## Why it matters

Scheduled tasks are one of the most common persistence mechanisms because they
run code on a trigger (logon, a time, an event) with no user present — and
they're trivial to create. Attackers use them to re-launch malware after reboot
or to run on a schedule that blends into normal activity. The flip side is that
plenty of legitimate software creates tasks too, so this is a medium-severity,
context-matters signal rather than a wake-someone-up alert.

## What a true positive looks like

A task created by an unexpected account that runs a script, a binary from a
suspicious path, or an encoded PowerShell command — especially one created
shortly after other suspicious activity. The task action and the creating user
are the key context.

## Common false positives

- **Software installs and updates** routinely create scheduled tasks. This is
  the main source of noise. Allowlist the installer account or known
  software-management host:
  → allowlist `user: SYSTEM` on managed hosts, or `host_pattern: ws-*` for fleet imaging.
- **IT automation / RMM** creating maintenance tasks. Allowlist the RMM account.

This rule honours these allowlist scopes (tune without editing the rule):

- `user`
- `user_pattern`
- `host`

## Tuning knobs

None — single-event trigger. Because legitimate task creation is common,
allowlisting the noisy-but-benign accounts is the main tuning lever here.
