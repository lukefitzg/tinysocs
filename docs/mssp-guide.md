# TinySocs MSSP Deployment Guide

Guide for managed security service providers deploying TinySocs across multiple client environments.

## Architecture Overview

Each client gets an independent TinySocs TinyBox instance. No data leaves the client network. The MSSP monitors via webhook aggregation and optional remote dashboard access.

```
Client A Network          Client B Network          MSSP SOC
┌─────────────────┐      ┌─────────────────┐      ┌──────────────┐
│ TinyBox (all-in-│      │ TinyBox (all-in-│      │ Webhook      │
│ one) + Agents   │──────│ one) + Agents   │──────│ Aggregator   │
│                 │ webhook                │ webhook              │
│ OpenSearch      │      │ OpenSearch      │      │ Alert Triage │
│ Dashboard :8090 │      │ Dashboard :8090 │      │ Dashboard    │
└─────────────────┘      └─────────────────┘      └──────────────┘
```

## Per-Client Deployment

### Standard Deployment

1. Install TinySocs TinyBox on a dedicated VM or server at the client site
2. Deploy agents to monitored endpoints
3. Configure the webhook to point to your MSSP aggregation endpoint
4. Enable network dashboard access (HTTPS) for remote triage

### Configuration Per Client

Key settings to customise per client in `assistant.env`:

| Setting | Purpose | Example |
|---------|---------|---------|
| `DASHBOARD_BIND` | Network access | `0.0.0.0` for remote |
| `DASHBOARD_TLS_CERT` | TLS certificate path | Auto-generated |
| `DASHBOARD_TLS_KEY` | TLS key path | Auto-generated |
| `WEBHOOK_URL` | MSSP alert aggregation | `https://soc.mssp.com/hooks/clientA` |
| `WEBHOOK_SECRET` | HMAC signing secret | Unique per client |
| `LLM_API_KEY` | LLM provider key | Can share across clients |

### Credential Management

- Each client TinyBox has its own OpenSearch credentials (auto-generated during install)
- Dashboard passwords should be unique per client
- LLM API keys can be shared or per-client depending on billing preferences
- Webhook secrets must be unique per client for HMAC verification

## Webhook Aggregation

TinySocs sends alert webhooks with HMAC-SHA256 signatures. Your aggregation endpoint should:

1. Verify the `X-TinySocs-Signature` header against the client's webhook secret
2. Parse the JSON payload containing alert details
3. Route to your SOC triage queue, tagged by client

Webhook payload includes:
- Alert ID, rule ID, severity, description
- Affected host and user
- Timestamp and raw event data

## Monitoring Patterns

### Daily Operations

- Review aggregated webhooks for high/critical alerts across all clients
- Check daily summary emails (configured per client)
- Spot-check client dashboards for Fleet Health (agents reporting)

### Weekly Reviews

- Generate compliance reports per client for their framework (NIST/HIPAA/PCI)
- Review detection efficacy across client environments
- Check for clients with no alerts (may indicate agent issues)

### Monthly Reporting

- Export compliance reports as HTML for client delivery
- Compile detection metrics (alerts by severity, top rules, coverage)
- Review and tune detection rule thresholds per client environment

## Health Monitoring

Run `Test-TinySocsHealth` remotely or via scheduled task:

```powershell
# On client machine (scheduled task)
Import-Module "C:\Program Files\TinySocs\modules\TinySocs.Installer.psm1"
$results = Test-TinySocsHealth
# Forward failures to MSSP monitoring
```

Key health checks to monitor:
- OpenSearch service running (data store)
- Agent service running (event collection)
- Dashboard accessible (operator interface)
- Sysmon running (enhanced detection)

## White-Label Notes

TinySocs can be presented under your MSSP brand:

- Dashboard title and branding are in the embedded HTML template
- Daily summary emails reference "TinySocs" in the footer
- Compliance reports include "Generated by TinySocs" footer
- Webhook payloads include `source: "tinysocs"` field

To customise branding, modify the relevant templates before deployment or post-install.

## Scaling Considerations

| Endpoints | TinyBox Specs | OpenSearch Heap |
|-----------|--------------|-----------------|
| 1-10 | 4 CPU, 8 GB RAM | 2 GB (default) |
| 10-50 | 4 CPU, 16 GB RAM | 4 GB |
| 50-100 | 8 CPU, 32 GB RAM | 8 GB |

For >100 endpoints per client, consider a dedicated OpenSearch cluster rather than the bundled single-node instance.
