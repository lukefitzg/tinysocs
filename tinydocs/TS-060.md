# TS-060 — LSASS Memory Access

> A program opened the memory of `lsass.exe` — the Windows process that holds
> logged-in users' credentials.

## What it detects

A Sysmon process-access event (Event ID `10`) targeting LSASS, grouped by the
accessing process (`SourceImage`). One occurrence fires. Requires Sysmon with
ProcessAccess logging configured for LSASS. This is the behavioural cousin of
TS-061: TS-061 catches dumping *tools by name*, TS-060 catches the *act* of
reading LSASS regardless of the tool.

## Why it matters

LSASS memory contains password hashes, Kerberos tickets, and sometimes
plaintext credentials for everyone currently logged in. Reading it is the most
direct route to credential theft and the step that turns one machine into a
foothold for lateral movement. Catching the memory access itself defeats
attackers who rename their tools to dodge name-based rules.

## What a true positive looks like

A non-system process — a renamed binary, a script-spawned process, `rundll32`
calling `comsvcs.dll MiniDump`, or an unknown executable from a temp path —
opening LSASS with read/clone access rights. The legitimate openers are few and
well-known (AV, EDR, some Windows components).

## Common false positives

- **Antivirus / EDR products** legitimately inspect LSASS. Allowlist the
  security product's binary:
  → allowlist `process_path: C:\Program Files\<EDR>\sensor.exe`.
- **Windows components** (e.g. `wininit.exe`, some MsMpEng paths). Allowlist by
  exact path once confirmed benign.

This rule honours these allowlist scopes (tune without editing the rule):

- `process_path`
- `process_pattern`
- `user`

## Tuning knobs

None — single-event trigger. Allowlist your AV/EDR's exact path rather than
disabling the rule; the whole value is catching the *unexpected* reader.
