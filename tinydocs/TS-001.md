# TS-001 — Brute Force Logon

> The same user account just failed to log in many times in a few minutes —
> someone (or something) is guessing the password.

## What it detects

Failed-logon events (Windows Security Event ID `4625`) grouped by the target
user name. The rule fires when one account accumulates `15` failures within a
`5`-minute window. Counting by *user* (rather than source) catches password
spraying and repeated guessing aimed at a single high-value account.

> The companion rule **TS-002** counts the same `4625` events grouped by source
> IP instead, which catches one machine hammering many accounts. Run both —
> they cover different attack shapes.

## Why it matters

Failed logons are the most common first sign of an externally-facing account
under attack — exposed RDP, a VPN gateway, or a service account with a weak
password. Fifteen failures in five minutes is not a fat-fingered password; it's
automated. Catching it early, before the guess succeeds, is the difference
between "we blocked an attempt" and "we're doing incident response."

## What a true positive looks like

A steady stream of `4625` events for one account — often `Administrator`, a
service account, or a named user — with `LogonType` 3 (network) or 10 (RDP),
sometimes from an unfamiliar or foreign source IP. The failures stop abruptly if
the attacker succeeds (watch for a `4624` success right after — that's the bad
ending).

## Common false positives

- **A user with a saved/expired credential** (mapped drive, Outlook profile,
  scheduled task) re-trying a stale password in a tight loop. Fix the saved
  credential; if it's a known service identity, allowlist it:
  → allowlist `user: svc_backup` with a note about the maintenance window.
- **A vulnerability scanner or pentest** sweeping auth. Allowlist the scanner's
  subnet:
  → allowlist `source_ip_cidr: 10.50.0.0/24`.

This rule honours these allowlist scopes (tune without editing the rule):

- `user`
- `user_pattern`
- `host`

## Tuning knobs

`threshold` (default `15`, range `3`–`75`). Lower it on environments where any
brute force is unacceptable and benign retry loops have been allowlisted; raise
it if a noisy-but-legitimate retry pattern can't be cleanly allowlisted. Prefer
allowlisting the specific benign account over globally raising the threshold —
raising it weakens the rule for *every* account.
