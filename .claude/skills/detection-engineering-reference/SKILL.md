# Detection engineering reference

Domain theory for TinySocs's C# detection engine (`src/TinySocs.Agent/Detection/DetectionEngine.cs`) — the **only engine that fires alerts in production** (see CLAUDE.md's dual-engine section; `tinysocs-architecture-contract` owns the full dual-engine story). This skill is the event-ID dictionary, the exact matching semantics, the MITRE mapping, and the false-positive theory an engineer needs before touching a rule.

All facts below are date-stamped **2026-07-11** against `packaging/detection/rules.yml` (39 rules, the file `RuleLoader.cs` parses for the shipped installer), `integrations/sysmon/sysmon-config.xml`, `src/TinySocs.Agent/Detection/DetectionEngine.cs`, `src/TinySocs.Agent/Detection/DetectionRule.cs`, `src/TinySocs.Agent/Inputs/FileIntegrityInput.cs`, and `docs/pilot-ruleset.md`. Rule counts: **19 enabled** of 39 C#-engine rules (18 non-lab disabled for v2 tuning + 2 lab-threshold variants TS-001-lab/TS-030-lab), 50 more in the non-running Python KQL catalogue (`src/tinysocs/agent/detections/rules.yaml`) — 89 total, per CLAUDE.md's honest-count rule. Don't conflate; if you state a rule count, say which of the three numbers you mean.

FIM field-naming quirk worth calling out for anyone authoring a new FIM rule: FIM events use a body-level `FilePath` (capital F, capital P) as the natural `group_by` key, not a `winlog.event_data.*` dotted path like the Windows-native rules. TS-113 additionally groups by `winlog.computer_name` — added specifically to FIM events on 2026-07-08 (`FileIntegrityInput.cs:575-582`) to give them host identity; before that fix TS-113 could never form a group key and was dead (see `docs/pilot-ruleset.md`'s "Two dead rules found while proving all 19" section). Don't assume `winlog.computer_name` is present on every FIM event type without checking — it was added as a deliberate fix for one rule's grouping need, not a blanket convention.

## 2. `threshold_by_key` matching semantics (from `DetectionEngine.cs`)

There is exactly **one** rule type today: `threshold_by_key` (`DetectionEngine.cs:75`, `DetectionRule.cs:14` comment lists `match_single`/`cardinality` as aspirational — neither is implemented). Every rule in `packaging/detection/rules.yml` uses it.

Evaluation order per incoming event (`EvaluateEvent` → `EvaluateThresholdByKey`, `DetectionEngine.cs:188-325` for the window/threshold/cooldown logic, condition-matching split out into `EventMatchesCondition`, `:329-376`):

1. **`event_id`**: exact integer match. `evt.EventId != condition.EventId.Value` → no match (`DetectionEngine.cs:332`).
2. **`channel`**: case-insensitive exact match via `string.Equals(..., StringComparison.OrdinalIgnoreCase)` (`:338-342`). Omitted `channel` in a rule means "any channel."
3. **`field_match`** (optional, `:345-373`): the field at `field_match.field` (dot-path, same resolver as `group_by`) must contain (default) or exactly equal (`match: "exact"`) one of `field_match.values`.
   - **contains** (default): `fieldValue.IndexOf(pattern, StringComparison.OrdinalIgnoreCase) >= 0` — case-insensitive **substring**. `TS-061`/`TS-062`/`TS-090`/`TS-130`/`TS-131`/`TS-132`/`TS-134`/`TS-135`/`TS-136`/`TS-082` all use this default.
   - **exact**: `string.Equals(fieldValue, pattern, StringComparison.OrdinalIgnoreCase)` — full-string, case-insensitive. Only `TS-071` uses `match: "exact"` (`LogonType` must be the literal string `"10"`, not merely contain it — important because `"10"` as a substring would also match a hypothetical `"100"`, `"1023"`, etc.).
   - If the field is missing from the event entirely, the match fails (returns false), the event is dropped for this rule — it is **not** treated as a wildcard pass.
4. **`group_by`** (`ExtractGroupKey`, `:378-`): dot-path into `AgentEvent.Body` (e.g. `winlog.event_data.TargetUserName`). If the configured `group_by` field resolves to null/empty, the engine **falls back to `winlog.computer_name`** (`:196-211`) rather than dropping the event outright — logged at Debug level ("falling back to computer_name"). **If `winlog.computer_name` is also missing, the event is silently dropped** (`return null`, no group key at all) — this is the exact failure mode that made TS-113 dead before its 2026-07-08 fix.
5. **Sliding window**: events accumulate per `{ruleId, groupKey}` in an in-memory dictionary (`_windows`), added to the window at `:230-234`. For `threshold > 1`, events older than `window_minutes` are pruned from the window **before** the count check on each new event (`:246-249`) — this is a genuinely sliding window, not a fixed bucket. A background pass also prunes every `_windows` entry every 500 evaluations (`PruneExpiredWindows`, `:95-186`) to bound memory.
6. **`threshold <= 1` fast path** (`:240`): window cleanup is skipped entirely — the rule fires on the very first matching event with no window-pruning overhead. Rationale in the code comment: avoids false negatives when events are processed with delay (queue backlog, shipper retries).
7. **Cooldown**: `effective_cooldown = cooldown_minutes if cooldown_minutes > 0 else window_minutes` (`:254-258`) — **cooldown defaults to the window length if unset**, not to zero. While in cooldown, the alert is suppressed but the window is still cleared (`:260-271`, the `window.Clear()` at `:266`) — so cooldown does not let events silently accumulate past threshold; it resets the counting entirely.
8. **Alert ID**: deterministic, `"{rule.Id}|{groupKey}|{windowStart:yyyy-MM-ddTHH:mm:00Z}"` where `windowStart` is the earliest event in the firing window, **rounded down to the minute** (`RoundDownToMinute`; ID built at `:277-283`, alert object built at `:288-311`). Same rule + same key + same firing minute → same alert ID, which is what makes alert deduplication in OpenSearch idempotent on retry/replay.
9. On fire, the window is `Clear()`ed (`:313-314`) — a rule cannot re-fire on the same accumulated events; it needs a fresh set to reach threshold again.

Field-resolution note: `group_by` and `field_match.field` share the same dot-path resolver (`ExtractGroupKey`, reused for both) — it walks `AgentEvent.Body` as nested `Dictionary<string, object?>` splitting on `.`. There is no array-index or wildcard support; a path segment that doesn't exist as a dict key returns null immediately, it does not throw.

For rule format v2 fields (`runs_on`, `allowlist_scopes`, `baseline`, `tuning`) layered on top of this schema in the signed pack — see `tinysocs-architecture-contract` (schema/trust-path ownership) and `tinysocs-research-frontier` (allowlist/baseline runtime status: schema-present, **not enforced by `DetectionEngine.cs`** as of 2026-07-11 — zero references to "allowlist" in `src/TinySocs.Agent`).

## 4. False-positive theory for a quiet SMB office

Source: `docs/pilot-ruleset.md` — "Who this list is for" and the per-rule notes. Quoted reasoning, not paraphrase, where load-bearing.

**The ICP and the bar.** Per `docs/icp.md`: a 20–150-person Windows/M365 shop with zero security staff — one IT generalist or an outsourced MSP, pushed into monitoring by an insurer, an audit, or a customer questionnaire. Every alert in week one is read by someone who has never triaged a security alert before. Three tests every enabled rule must pass:
1. Low FP in a normal SMB estate — standard business software, auto-updaters, maybe an RMM agent. No red team, no dev tooling assumptions.
2. High signal when it fires — worth a phone call.
3. **"Explainable in one sentence to a non-technical person."**

**The governing rule: "When in doubt, a rule stays off."** A first pilot that cries wolf on day one kills the "someone competent is watching" promise the subscription is built on.

**Why 15-failures/5-min beats a lower threshold like 6** (TS-001): "a human mistyping stops at 3–5. Fifteen failures in five minutes against one account is automation. The classic benign cause — a service or mapped drive with a stale saved password — retries slower than this in most cases, and when it does trip the rule, the fix (update the stale credential) is worth doing." The threshold is chosen to sit *above* the natural retry cadence of the most common benign trigger (a stale-credential loop) and *below* nothing a human would ever hand-type.

**Why every-7045 was a three-alert duplicate** (TS-070/TS-072/TS-090, pre-pilot-cut): none of the three had the field filter its description claimed (PsExec name, non-standard path, suspicious path) — "one legitimate install currently produces three differently-named alerts." The pilot cut resolved this by giving TS-070 and TS-090 real `field_match` filters and disabling the now-redundant generic TS-072 — the opposite of the original draft plan, which would have kept TS-072 and disabled the other two. Reasoning: naming the two malicious 7045 patterns specifically is strictly higher fidelity than a generic "a service was installed" catch-all.

**Why TS-134 (`obfuscated_command`) is "the single most dangerous rule for pilot credibility":** it matches `-enc`, `-EncodedCommand`, `FromBase64String`, `iex(`, `Invoke-Expression` in any command line at threshold 1. "Legitimate vendor installers, deployment scripts, and **especially RMM agents** (the tooling of the exact MSP channel in the ICP) use encoded PowerShell constantly." An MSP-channel pilot install running this rule enabled would alert on the MSP's own routine tooling, on day one, undermining the entire pitch. Off until v2 allowlists exist.

**Other rules disabled for the same "day-one alert fatigue" class** (all documented in `docs/pilot-ruleset.md`'s "Will alarm on normal behaviour" section): TS-092 (Sysmon logs every `.exe`/`.dll`/`.ps1`/`.bat` write, every Downloads write, every Outlook attachment — "fires dozens of times on day one"), TS-091 (~113-entry Sysmon registry include list — "every installer and updater trips it"), TS-135 (Windows itself spawns rundll32 routinely for printing/control-panel/thumbnails — "3-in-5-min is normal desktop behaviour"), TS-136 (RMM/SCCM/monitoring agents spawn via WMI all day), TS-083 (Chrome's updater is a "famous FP" for timestomp), TS-040/TS-050 (volumetric process-creation bursts fire on builds/updates/login storms).

**Mislabeled rules fixed by the pilot cut, not just disabled** (§1 of `docs/pilot-ruleset.md`'s Implementation status): TS-071 previously claimed LogonType filtering in its description with **no such filter in the condition** — as shipped pre-fix it was TS-002 with a lower threshold, so the same attack produced two differently-named alerts. TS-070/TS-090 similarly claimed a filter they didn't have. All three got real `field_match` clauses in the pilot cut (§1 above documents the resulting conditions).

## 5. Windows semantics quirks the project depends on

- **4625 `IpAddress` "-" lumping**: local/interactive logons often carry `IpAddress: "-"` rather than a real address. TS-002 (`brute_force_logon_by_ip`) groups by this field, so all such local-logon failures across *every* account on a box collapse into a single group key `"-"` — a real behavioral quirk to know before tuning TS-002's threshold or explaining an alert to a customer (`docs/pilot-ruleset.md`, rule #6).
- **Windows' automatic "suspicious" 4104 logging is claimed to bypass the ScriptBlockLogging policy** for certain string patterns: the theory is that even with `EnableScriptBlockLogging` unset (true for every current TinySocs production install — nothing in the installer or `Deploy-AgentUpdate.ps1` sets it), Windows PowerShell's built-in heuristic still emits a 4104 event when a script block contains flagged strings, including the AMSI-bypass strings TS-082 matches (`AmsiUtils`, `amsiInitFailed`, `AmsiScanBuffer`, `SetValue(null`). This is offered as why TS-082 is reliably enabled while TS-030 (raw scriptblock *volume*) is not — TS-082 supposedly rides on automatic suspicious-content logging, TS-030 needs the full policy. **This specific "works with the policy unset" claim is not actually harness-confirmed**: `docs/pilot-ruleset.md` is internally inconsistent about TS-082 — its 2026.27 harness-run summary lists TS-082 among "four enabled rules remain untested here (env-limited): TS-082 (needs Defender RTP off)..." (line ~64), while the per-rule write-up (rule #4) and the pilot-conversation summary both mark it "✅ DETECTED" / harness-validated. Neither passage says the harness ran with the GPO deliberately left unset — and `tests/Test-AtomicDetection.ps1:696-699` explicitly sets `EnableScriptBlockLogging=1` before every atomic run, which would mask this exact question if that harness produced the "DETECTED" result. Treat "TS-082 fires without the policy" as an unverified theory, not a confirmed fact, until someone reconciles the doc and re-runs with the GPO deliberately off.
- **`sqldumper.exe` ships with SQL Server** and runs automatically on a SQL Server crash dump. It's in TS-061's credential-dumping-tool `field_match` list (alongside mimikatz/procdump/nanodump/pwdump/gsecdump/wce.exe/dumpert/lsassy) — an SMB running SQL Server Express could legitimately trigger TS-061 on a crash. `docs/pilot-ruleset.md` rule #8 flags pulling `sqldumper.exe` from the list for SQL-Server pilots as an open tuning question. `procdump` is the other named exception — a legitimate sysdamin/dev tool, rare in this ICP but common in dev-heavy shops.
- **4663 needs a SACL on the object, not just auditpol.** Enabling the `File System` audit subcategory alone produces nothing; the target file/registry key also needs its own System Access Control List configured for auditing. TS-062's watchlist (ntds.dit, SAM/SYSTEM/SECURITY hives) assumes this SACL exists — mostly true on a domain controller by default, not guaranteed on a workstation.
- **Command-line auditing (`ProcessCreationIncludeCmdLine_Enabled`) is a separate policy from process-creation auditing (4688 itself).** A host can have 4688 flowing with no `CommandLine` field populated. This is exactly why TS-130/TS-131 key on `NewProcessName` (the binary name) rather than command-line content — see the inline comment at `packaging/detection/rules.yml:766`: "Matches on process name (CommandLine auditing is not guaranteed enabled)."

## When NOT to use this skill

- Adding a new rule, writing its Atomic Red Team test, or proving it fires end-to-end → **tinysocs-detection-validation-toolkit**.
- Deciding whether a candidate rule is good enough to promote/enable, or how the pilot-cut FP-vs-coverage tradeoff should be re-litigated for v2 → **tinysocs-research-methodology**.
- The dual-engine architecture itself (why the Python catalogue doesn't run, the signed-pack trust path, FIM as a synthetic-event subsystem) → **tinysocs-architecture-contract**.
- What counts as harness evidence, xUnit test structure, banned efficacy numbers → **tinysocs-validation-and-qa**.
- Fixing the stale `detection-coverage.md` / restarting the validation dashboard cadence as an actual campaign → **tinysocs-validation-publication-campaign**.
- Rule config knobs, env vars, ports → **tinysocs-config-and-flags**.
- Debugging a specific silent-rule symptom in a running install → **tinysocs-debugging-playbook**.

Any change to which rules are enabled, their thresholds, or their MITRE claims changes detection behavior and public-facing coverage claims — gate through **tinysocs-change-control**.
