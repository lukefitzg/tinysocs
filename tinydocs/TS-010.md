# TS-010 — Local Account Created

> A new local user account was created on this machine.

## What it detects

A user-account-creation event (Windows Security Event ID `4720`), grouped by the
new account name, firing on the first occurrence (with a 60-minute cooldown to
avoid duplicate alerts). It catches accounts created directly on a machine, not
in Active Directory.

## Why it matters

Creating a new local account is a simple, durable persistence and backdoor
technique: an attacker adds an account they control so they can log back in even
if the original compromised credential is reset. On servers and workstations,
new local accounts are uncommon and usually deliberate IT actions — so an
unexpected one, especially one added to the Administrators group, is worth a
look.

## What a true positive looks like

A new local account appearing on a machine without a corresponding IT ticket,
often with an innocuous-looking name (`support`, `admin2`, `svc-update`),
sometimes immediately added to a privileged group, created by an unexpected
account or shortly after another alert.

## Common false positives

- **Routine IT provisioning** — building a new machine, adding a local service
  account. Allowlist the provisioning host or the known service-account name:
  → allowlist `user: svc-monitoring` or `host_pattern: imaging-*`.
- **Software installers** that create dedicated local service accounts.
  Allowlist the specific account name once confirmed.

This rule honours these allowlist scopes (tune without editing the rule):

- `user`
- `user_pattern`
- `host`

## Tuning knobs

None — single-event trigger. Allowlist known service-account names or the
imaging host rather than disabling; the value is catching the *unexpected*
account.
